# Contributing

The [README's Contributing section](README.md#contributing) says what is most
valuable. This file adds the practical part: what a submission needs to contain,
and what happens to it.

## The two contributions worth the most

**1. A case that breaks something.** A shape whose real-org behaviour differs
from what any reasonable analyzer would predict. That is the whole point of the
corpus, and a case that surprises is worth more than ten that confirm.

**2. An org verdict for one of the seven.** Seven cases carry no verdict because
an org cannot measure the absence of an analyzer's knowledge
([ADR-003](docs/adr/ADR-003-seven-cases-carry-no-verdict.md)). If you find a way
to make a platform adjudicate one of them, I would rather be wrong about the
label than keep it.

Also welcome, and in this order:

- **A case that stops reproducing on a later release.** The corpus was measured
  on Summer '26. Platform behaviour moves; a case that no longer holds is a
  finding, not a bug report.
- **A defect in a published value.** v1.1 exists because one derived field was
  wrong for five of twenty-one cases. If another one is wrong, saying so is the
  most useful thing you can do.
- **A weak label that should be stronger.** Four cases are labelled `reasoned`
  and three `platform-doc`. Both mean *not measured here*. Measuring one moves it
  up.

## What a case submission needs

A case is only usable if someone else can reproduce it. Please include:

| | |
|---|---|
| **The Apex** | The exact source, small enough to read in one screen |
| **API version** | The version the class is compiled at — it changes the answer |
| **The user** | Profile, permission sets, and the sharing the record has |
| **What the org did** | The observation, not the interpretation — rows returned, DML landed, field present |
| **How you observed it** | Anonymous Apex, a test, the oracle — so the observation can be repeated |

The last row matters most. Every case in the corpus carries
`label_provenance` naming where its ground truth came from, and that field is
the benchmark's real quality metric
([ADR-002](docs/adr/ADR-002-provenance-is-published-per-case.md)). A case
arrives with the provenance its evidence supports, not the provenance one would
prefer.

## What will not be accepted

- **A case whose expected outcome was reasoned rather than measured**, submitted
  as measured. It can still go in — labelled `reasoned`, which is what that label
  is for.
- **A correction typed directly into `CHECKSUMS.md`.** That file is generated by
  the exporter and never edited
  ([ADR-004](docs/adr/ADR-004-the-seal-is-generated-never-typed.md)).
- **A silent fix to a published value.** Anything that changes what a previous
  version said gets an errata entry and a version bump
  ([ADR-005](docs/adr/ADR-005-errata-over-silent-correction.md)).

## Verifying locally

Everything CI runs, you can run:

```bash
grep -E '^    [0-9a-f]{64}  ' CHECKSUMS.md | sed 's/^ *//' | sha256sum -c
```

CI additionally checks that the corpus agrees with itself — counts match the
lists, every referenced case file exists, no case file is unreferenced, ids are
unique, `label_provenance` is a recognised value — and that the provenance
distribution quoted in the README still matches `corpus.json`.

That last check exists because the README used to repeat the corpus hash, and
that copy went stale the first time the corpus was regenerated. Prose that
restates data is a copy that can drift, so the copy is now checked rather than
trusted.

## Decisions

The methodology is recorded in [`docs/adr/`](docs/adr/) — five records covering
why the oracle is a live org, why provenance is published per case, why seven
cases carry no verdict, why the seal is generated, and why a defect gets an
errata entry rather than a quiet correction.
